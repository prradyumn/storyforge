# Working on StoryForge

Read `docs/HANDOFF.md` first: it explains what the product is, how it is
deployed, what the UI is built on, the eval state and the open issues.

Conventions that matter here:

- `pytest -q` and `ruff check .` must pass before any commit. Tests are offline; never add a test that needs a key.
- Prompts in `storyforge/prompts/vN/` are never edited. A change is a new version, measured with `eval/run_eval.py` on the same golden set, and written up in `eval/DECISIONS.md` with before/after numbers. The README table is generated by `scripts/render_eval_table.py --write`, do not edit it by hand.
- `web/index.html` stays a single file with no build step; style through the CSS tokens in `:root`; escape every model string with `esc()` before `innerHTML`.
- Secrets live only in `.env` (gitignored) and hosting dashboards. `.env.example` lists the names.
- Both Vercel (front end) and Render (API) auto-deploy from `main`. `vercel.json` rewrites `/api/*` and `/docs` to Render; keep it in sync if routes change.
- Write in plain prose in docs and commit messages; the project's voice is measured, specific, and avoids hype.
